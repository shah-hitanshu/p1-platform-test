# P1 SDK 0.8 — Persistent-Editor Migration Tooling

**Date:** 2026-07-27 · **Ticket:** PCC-3471 · **Stacks on:** `refactor/use-p1-plugins` (PR #134)

## Context

PR #134 moves the P1 editor from the catch-all **page** of `/p1/[[...p1]]` to a persistent
**layout** inside an `(editor)` route group. Next.js remounts page segments when route params
change, so the old structure tore down the entire editor — providers, auth, Puck, the canvas
iframe — on every document switch. Rendering from a layout at a static segment fixes that.

The change is **breaking for `@pantheon-systems/p1-next-sdk` consumers** who scaffolded from the
starter. After upgrading, `createP1Pages()` returns a `Layout`, `Page` is empty, and `EditorClient`
takes no props. An app that still has only `app/p1/[[...p1]]/page.tsx` (`export default pages.Page`)
renders a blank editor: TypeScript users hit a compile error from the changed prop type, but
JavaScript users get **no signal at all**.

The packages are pre-1.0 (`fixed` changeset group), so this ships as a **minor → 0.8.0**, with the
break documented in prose. Install-time migration is deliberately avoided: a `postinstall` codemod
runs in CI and on every install, and pnpm 10+ (this repo uses pnpm 11) does not run dependency
lifecycle scripts unless the consumer allowlists the package. The model is **auto-detect,
one-command-apply** — the convention used by `@next/codemod`, React, MUI.

## What was built

Three stacked branches, each merging into PR #134 for independent review.

### 1. Dev-mode detection warning (`packages/p1-next-sdk/src/pages-handler.tsx`)
A module-scoped `layoutRendered` flag, set synchronously at the top of `Layout` (before any
`await`). A parent layout always renders before its child page within a request, so a correctly
mounted editor flips the flag before `Page` reads it. A legacy page-only app renders `Page` alone,
and `Page` emits a one-time, dev-only (`NODE_ENV !== "production"`) warning pointing at the codemod
and this guide. Best-effort by design (module state is per-process); never runs in production, never
affects output. The TS signature break and the changelog remain the floor.

### 2. The `p1-migrate` codemod (`packages/p1-next-sdk/bin/`)
`npx @pantheon-systems/p1-next-sdk p1-migrate` — hand-written ESM JS modeled on
`create-p1-starter-kit` (shebang entry → thin `lib/`, pure-function transforms), shipped via `bin`
+ `files`. **No AST dependency** (none exists in the repo); the transform is dominated by one
deterministic rule — moving a file into the `(editor)` group prepends one `../` to each relative
import — plus two localized edits (`page.tsx` split, `EditorClientWrapper` signature) that
**template-match-or-bail**. All transforms run before any write, so a bail leaves the tree
untouched. Guardrails: clean-git-tree gate (`--force`), `--dry-run`, idempotent re-runs,
path-traversal guard on every write/remove. No new runtime dependency (plain-text messages).

**Proof of correctness:** the integration test reconstructs the OLD starter layout from
`git show main:…`, runs the codemod, and asserts the output is byte-identical to the current HEAD
`apps/p1-starter/app/p1/(editor)/` tree — the migration's own source of truth — plus
sibling-untouched, idempotency, and bail-on-divergence.

## Decisions

- **Minor, not major** — pre-1.0 semver-zero convention; the `fixed` group bumps all four packages
  to 0.8.0. A caret range never auto-jumps a minor, so no consumer breaks on a routine install.
- **String/regex over AST** — matches `build-template.js` precedent; the drift cases an AST would
  supposedly handle are exactly the ones the codemod should bail on, not fuzzily rewrite.
- **Detect-and-nudge, not install-time rewrite** — reliability (pnpm blocks the hook) and safety
  (a file-moving codemod needs a clean tree and a reviewable diff).
- **Open decision:** the changeset rides this tooling stack rather than PR #134, because its body
  references the `p1-migrate` command that only exists here. Revisit if #134 lands first.
