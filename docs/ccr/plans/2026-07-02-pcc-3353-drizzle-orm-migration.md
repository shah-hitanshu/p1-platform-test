# PCC-3353: Drizzle ORM Migration Plan

> **Scope of this document.** This is the umbrella plan for migrating the workers
> backend from hand-rolled SQL to Drizzle ORM. It fixes the architecture,
> the decision log, and the delivery boundaries. Each unit of work gets its own dated
> `docs/css/plans/` execution plan (with paired test plan) when it starts,
> following the house task-by-task convention. Status is tracked in PROGRESS.md,
> not in this file.

**Goal:** Replace the string-based `query(sql, params)` data layer with Drizzle
ORM so that the database schema has a single TypeScript source of truth, queries
are type-checked against that schema, row types are inferred instead of
hand-maintained, transactions are structured instead of stringly-typed, and
future schema changes are generated by tooling instead of written by hand.

**Non-goal:** introducing a data-access architecture. Queries move to Drizzle
where they already live. What sits on top of them — a repository layer,
per-domain query modules, something else — is a separate decision the team makes
later, against a codebase where every query is already typed (D3).

**Architecture:** Cloudflare Workers backend (`workers/collaborative-state/`), PostgreSQL via
Hyperdrive in production and direct connection in local dev, `postgres` (postgres.js)
as the driver. All SQL today funnels through one chokepoint, `query()` in
`workers/collaborative-state/src/db.ts`, with request-scoped connections held in AsyncLocalStorage
and a `max: 1` pool per request. Drizzle layers on top of the existing
postgres.js client, so the connection architecture (Hyperdrive, request scoping,
`prepare: false`) is unchanged.

**Tech stack:** `drizzle-orm` (postgres-js driver adapter), `drizzle-kit`
(schema introspection, migration generation, and the migration journal),
existing `postgres@^3.4` driver.

## Decision log

### D1 - Drizzle, used SQL-first

Drizzle is the target ORM: it is a thin, dependency-free layer over SQL that
runs natively in Workers, supports the postgres.js driver we already use, and
its query builder maps 1:1 to the SQL we already have (no ActiveRecord-style
abstraction to fight). Usage policy: prefer the query builder; embed `sql`
template fragments inside builder calls for operators the builder lacks (jsonb
merge, `ANY(array)`); whole-query `db.execute(sql...)` is an escape hatch
reserved for the cases listed in D6.

### D2 - Keep the postgres.js driver and the per-request connection lifecycle

`drizzle-orm/postgres-js` wraps the existing `postgres()` client. Hyperdrive
settings (`prepare: false`, `max: 1`, timeouts) stay exactly as they are in
`createDatabaseConnection`. `runWithConnection()` keeps its role as the request
boundary — it creates the connection, retries once on a connection-level error,
and closes fire-and-forget — and gains one responsibility: it builds the Drizzle
instance and enters it into the executor scope for the duration of its callback
(D4). Its call sites do not change.

The fire-and-forget close and the retry path are preserved as they are; both
exist for Hyperdrive pathologies documented in `src/db.ts`, not for the query
API.

### D3 - Queries are ported where they live; the test seam moves to the driver

The migration unit is the call site. A `query('SELECT ...')` becomes a Drizzle
builder call in the same function of the same file, and nothing moves between
modules. No `src/repositories/` layer is introduced by this migration.

Three reasons. Every PR stays a mechanical translation whose correctness a
reviewer can check line by line, with no design argument riding along. The
useful shape for an abstraction is far easier to see once 394 queries are typed
and visible than it is now, from a plan. And a layer chosen up front becomes a
constraint on 50 files that have to adopt it whether or not it fits them.

Choosing what sits on top — a repository layer, per-domain query modules,
something else — is deliberately left as follow-up work for the team. Nothing in
this migration blocks it, and the type-checked call sites are what make the
choice informed.

**The unit-test seam.** 93 test files mock `src/db`'s `query()`, stub rows, and
in 15 of them assert on the SQL string. Drizzle deletes that function, so the
seam moves down to Drizzle's own session. `tests/__stubs__/database.ts` builds a
real Drizzle instance over a client that never connects and replaces
`session.prepareQuery`. Rows come back exactly as the test wrote them, so
Drizzle's positional field mapping is never reimplemented.

Stubs are keyed by table and operation — `on(sites).select.returns([...])`. A
test says what a query against a table returns without restating the query, and
a query no test stubbed returns no rows, so adding an unrelated query to the code
under test does not disturb a test that never stubbed it. Recorded calls are
available as `calls(sites).insert` and `statements`.

The handle is ambient (D4). `stubDatabase()` installs its handle as the fallback
`db()` returns outside any scope, so a test constructs the stub in `beforeEach`
and calls the subject directly. No module is mocked. (Vitest runs each test body
in an async context detached from its hooks, so a scope opened in `beforeEach`
would not reach the test; the fallback exists for that reason, and nothing in
`src` may install one.)

What that gives each category of existing test:

- Row-stub mocks keep working. Rows are checked against `$inferSelect` instead of
  being free-form objects.
- SQL-string assertions are deleted, not rewritten. What SQL Drizzle emits is
  Drizzle's business; the unit test asserts on what the code did with the rows.
- Transaction sequencing is not observable here, and neither is the SQL. Both
  belong in `tests/db` against a real Postgres.

Real-Postgres coverage in `tests/db` is added by judgment, for queries whose
correctness is not evident from reading them: the two recursive CTEs, the cascade
deletes over `= ANY(uuid[])`, the partial-index upsert, the bulk version insert,
and every transactional path.

### D4 - The database handle is ambient, held in a request scope

Ported code reaches the database through `db()`, which returns the current
`Executor` (`Database | Transaction`) from an `AsyncLocalStorage<Executor>`
store. No function takes a database handle as a parameter and no route context
carries one. `runWithConnection` enters the store for the duration of its
callback, so everything reached from a request, a queue message, a Durable
Object call or a script is on that scope's handle without being told.

**Transactions.** `transaction(fn)` is `db().transaction((tx) => store.run(tx,
fn))`. Inside `fn`, at any depth, `db()` returns `tx`; a nested `transaction()`
gets a SAVEPOINT from Drizzle. This is what makes the ambient design safe rather
than merely convenient: code inside a transaction cannot leave it, because there
is no other handle to reach for. With a handle passed by argument, a participant
handed the base handle instead of `tx` opens a second connection, and with a
one-connection pool that is a hang until `statement_timeout`; only a reviewer
would catch it.

**Why not an explicit parameter.** The first three ports measured the cost. In
the auth slice, 25 route files, the route context types, 91 `assertPermission`
call sites and about 44 specs changed only to carry a handle: several times the
size of the SQL being ported, in PRs that could not be reviewed at that size.
The parameter bought one thing, a compile-time guarantee that a function has a
database. The ambient design gives that up and replaces it with the rules below.

**What the ambient design has to get right.** The failure it must not repeat is
PCC-3797: a Durable Object called a service outside any scope, the ambient
lookup threw, a broad catch logged a warning, and production ran with a null
organization for weeks. The spec passed because it mocked `src/db`, which made
`query()` succeed whether or not a scope existed.

- `db()` outside a scope throws `NoDatabaseScopeError`, a distinct class whose
  message names the scope helper. A catch that would swallow it rethrows it.
- Tests never mock `src/db`. The stub reaches the code under test through the
  scope fallback it installs on construction (`installDatabase`, test-only,
  ESLint-guarded out of `src`); an open scope always wins over it. A Durable
  Object or queue spec stubs the connection factory instead, so it proves the
  entrypoint opens its own scope.
- Work handed to `ctx.waitUntil` runs after the request scope has closed and
  opens its own.
- `AsyncLocalStorage` needs `nodejs_compat`, which the worker already has for
  the legacy connection store.

Consequences:

- A port changes the service file and its spec and nothing else. Signatures
  across services and routes are unchanged.
- The two `ROLLBACK TO SAVEPOINT` sites in `branch-document-service.ts` become
  nested `transaction()` calls.
- The 13 raw `BEGIN` sites become `transaction()` calls. Today they depend on
  `max: 1` for correctness, since every later statement in the request has to
  land on the one connection the `BEGIN` went down. Once they are callbacks the
  pool width is a tuning decision under D2, not a correctness constraint.
- The legacy `connectionStorage` and the executor store run side by side until
  teardown; `runWithConnection` enters both. The legacy store is deleted with
  `query()`; the executor store is permanent.

This supersedes the earlier D4, under which the handle was a parameter. PRs
#155 to #157 were built to that decision and are re-cut to this one.

### D5 - No shim; the two APIs coexist without one

`query()` is not reimplemented on top of Drizzle. A shim would change the
execution path of all 394 call sites in one commit only to be deleted at the end,
and it could not preserve their behaviour anyway: routed through Drizzle,
arbitrary SQL has no schema to map against, so values arrive unparsed for exactly
the reasons D12 sets out.

The two APIs share a request scope but not a connection. `runWithConnection`
enters the legacy store and the executor store together, and D12 gives each its
own client, so a legacy `query()` issued inside a Drizzle `transaction()` runs on
the other connection, outside the transaction, and a Drizzle query issued after a
legacy `BEGIN` does the same in reverse. Nothing bridges them.

Coexistence is handled by ordering the work instead (see Delivery). Waves are
drawn by call graph and merge together, so no legacy `query()` ever runs inside a
Drizzle transaction and no Drizzle query ever runs inside a legacy `BEGIN`.

The one rule this leaves: a function that queries inside a transaction must be in
the same wave as the transaction that calls it. The call-graph pass that opens the
work is what enforces it, and a cheap tripwire backs it up: legacy `query()`
throws when the executor store holds a `Transaction`, so a call path the pass
missed fails in the integration tier instead of committing half a transaction.

### D6 - What stays raw SQL

- The bulk version-insert query (`document-version-service.ts:960-1006`). It is
  correct, tested, and performance-sensitive; it is ported as a
  `db.execute(sql...)` with typed result mapping, not a builder rewrite.
- The plpgsql trigger and function (from legacy migration 022), the time-fenced
  content constraint (from 049), the implicit `text -> uuid` cast, object
  comments, and data conversions. Drizzle-kit generates DDL diffs only; this
  content lives in hand-written SQL inside drizzle-kit custom migration files
  (`drizzle-kit generate --custom`) — `0001` for the cut-over content and
  `0002` for the redirect path conversion carried over from legacy 053. Demo
  and mock seed content (from 006, 015, 037) leaves the migration path
  entirely for a dev-and-CI-only `db:seed` step (D9).

### D7 - Migrations: drizzle-kit owns the schema

`workers/collaborative-state/src/db/schema.ts` (bootstrapped by `drizzle-kit pull` against a fully
migrated local database, then hand-cleaned) is the source of truth for DDL, and
drizzle-kit's journal is the tracking system. The hand-rolled runner
(numbered files, `app.schema_migrations`) was removed in the same phase rather
than kept as a parallel system.

History cut-over:

- `0000_baseline` is generated from `schema.ts` and contains the full DDL as of
  the cut-over.
- `0001` is a custom migration carrying everything introspection cannot see:
  the `enforce_main_only_branching` function and trigger (legacy 022), the
  time-fenced `document_versions_content_present` constraint (legacy 049), the
  `pgcrypto` extension, the implicit `text -> uuid` cast, and the table and
  column comments.
- `0002` onward are ordinary migrations. Numbered migrations that landed after
  the cut-over are ported into the journal rather than left behind: `0002`
  carries legacy 053's redirect path conversion, written so a database that
  already ran the numbered version takes it as a no-op.
- Fresh databases (CI, new dev machines) are built by the migrator from the
  journal. Existing databases must never execute 0000/0001; `src/db/baseline.ts`
  records the corresponding journal rows instead, keyed on
  `app.schema_migrations` recording the last numbered migration that changed
  structure. Anything generated after the baseline cutoff runs normally.

What is kept from the old runner is its operational knowledge, not its code:
the applier is a small script using Drizzle's programmatic `migrate()`
(`drizzle-orm/postgres-js/migrator`), so the Cloud SQL Auth Proxy path and
`POSTGRES_SET_ROLE=cssuser` object-ownership setup carry over unchanged. npm
script names (`pnpm db:migrate`) and the deploy workflow are as they were.

`app.schema_migrations` is left in place, inert, in existing environments and
dropped in a later cleanup — it is also the baseline signal, so it cannot be
dropped until every environment is baselined. Drift protection comes from CI:
`drizzle-kit generate` runs on every PR and the build fails if it produces
anything, which means `schema.ts` described something no migration creates.
Nothing detects an edit to an already-applied migration — the migrator selects
by journal timestamp and never re-checks hashes, and `drizzle-kit check` only
looks for collisions inside the journal — so treating applied migrations as
immutable is a convention, enforced by review rather than by tooling.

### D8 - Row types come from the schema

The 42 hand-maintained `*Row` interfaces are deleted as their queries port,
replaced by `typeof table.$inferSelect` / `$inferInsert`. Schema properties are
camelCase with explicit snake_case column names, which also eliminates the
per-service manual snake-to-camel mapping.

### D9 - Scope fence: no behavior, schema, or API changes

The migration produces byte-identical HTTP behavior and an unchanged database
schema. No query is "improved" while being ported; no table is renamed; the
frontend and the DO/queue/scheduled surfaces see no difference. Anything
discovered along the way (bugs, missing indexes, schema cleanups) is filed as
follow-up, not folded in. Deferring the abstraction question (D3) is not a
licence to restructure either: a port that moves a query to a different module
is out of scope the same way a rewritten query is.

**Approved exception (seed data).** The legacy migrations seeded demo/mock data
(demo sites, mock users, backfilled roles) wherever `db:migrate` ran, including
production if migrations were dispatched there. Under Drizzle this data moves to
a standalone `db:seed` script run only in local dev and CI, never production.
Fresh dev and CI databases remain identical to today; production stops receiving
demo rows. This is the one intentional behavior change in the migration, so the
Drizzle DDL migrations (0000/0001) contain schema only, and the cut-over parity
check compares schema, not seeded data.

### D10 - The query guard is driver configuration, in two layers

`runSqlUnsafe` currently provides three things that die with it: a 20-second
fail-fast race, failure logging keyed on `describeQuery`, and `rowCount`
normalization. Drizzle offers no hook to re-home them — its built-in
OpenTelemetry spans are compiled in but inert (`tracing.js` declares `let otel`
and nothing assigns it), its `logger` fires before execution and never sees the
outcome, and it has no interceptor or per-query timeout. Everything it executes
goes through `client.unsafe(query, params)`. So the guard belongs to the client
Drizzle is constructed over, in two layers:

1. **`statement_timeout` as a postgres.js connection option.** Postgres enforces
   the deadline and terminates the backend, where the current `Promise.race`
   abandons the promise and leaves the query running. Verified: a query rejects
   with `57014 canceling statement due to statement timeout` and the connection
   remains usable afterwards.
2. **A client-side deadline, using postgres.js `query.cancel()`.** Required
   because `statement_timeout` is server-enforced and cannot fire when the
   server never receives the statement. Verified: against a socket that accepts
   and never replies — the Hyperdrive pathology the original race documents — a
   client with `statement_timeout` set still hung indefinitely. Verified too
   that `cancel()` stops the backend rather than merely rejecting locally.

This layer also carries the `describeQuery` duration and failure logs, because
it is the only place that sees the outcome. It is permanent infrastructure, not
scaffolding: it replaces what `runSqlUnsafe` does today and outlives the last
raw query.

### D11 - Telemetry: spans need a provider before instrumentation is worth adding

Database observability today is structured logs, deliberately low-cardinality:
`describeQuery` reports operation and table and never the statement text,
because the text can embed customer content and would be an unbounded log
field. A related note in `db.ts` records why sqlcommenter is not applied per
request — Hyperdrive caches by query text, so a unique comment per request would
drive its hit rate to zero.

Target state is spans from `@kubiks/otel-drizzle` (2.1.0, no runtime
dependencies, peers `@opentelemetry/api >=1.9 <2` and `drizzle-orm >=0.28`),
which instruments the Drizzle instance and captures duration, errors and span
status — the outcome data Drizzle's own `logger` cannot provide.

Three things gate it:

- **No tracer provider exists.** `p1-telemetry` depends on `@opentelemetry/api`,
  `core` and `context-async-hooks`, propagates W3C `traceparent`, and stamps
  `trace_id` into logs, but nothing in the repo calls `getTracer` or registers a
  provider, and nothing creates a span. Without a global provider the API hands
  back a no-op tracer, so the patcher would emit nothing. Wiring a provider and
  exporter that work in workerd is its own task.
- **Workers support is unstated.** The package declares Node engines and lists
  Node frameworks. It has no runtime dependencies, so it may work under
  `nodejs_compat`, but it patches Drizzle internals and needs verifying in
  workerd rather than assuming.
- **`db.statement` carries the full SQL text**, which reverses the redaction
  decision above. Either drop that attribute in a span processor or decide
  deliberately to ship it.

Until a provider exists, the guard's logs (D10) remain the database's
observability, and the patcher is deferred to the parallel track below.

### D12 - Each handle gets its own client

`drizzle()` overwrites its client's parsers for the timestamp, date, time and
numeric-array OIDs, and its serializers for json and jsonb, so that it can map
values itself. Anything else holding that client then reads timestamps as strings
and throws when a parameter is an object.

So the Drizzle handle and the raw `query()` connection each get their own
postgres.js client, and closing the request scope ends both. A request opens two
connections while `query()` has callers and one once it has none; the second
client is deleted along with the raw path.

Separate clients mean a Drizzle transaction cannot see a legacy write, or the
reverse. Nothing bridges them: D5's ordering rule is what keeps the two out of
each other's transactions.

and never touches the raw query interface. The three backfills are ordinary
callers and convert with their wave.

Also in this wave: `app.document_versions.created_at` and
`app.agent_site_roles.created_at` are nullable with a `now()` default, so
drizzle-kit types them `Date | null` while the domain types declare
`createdAt: string`. Both mappers bridge that with `?? ''`, which yields an
Invalid Date for a row that in practice cannot exist, since no insert path
writes the column explicitly. The fix is `NOT NULL` on both columns rather than
a mapper change: it makes the schema types accurate and both fallbacks delete
themselves. It needs a null count against staging and production first, which
is why it was left out of the wave 3 tier 0 and layer 1 PR (#276), whose scope
excludes schema changes.

Exit criterion: no raw SQL execution outside `schema.ts`, the migration files and
the D6 exceptions; `postgres` is imported only by the db layer.

### 4. Coordinating the agents

Fan out within a wave, barrier between waves. Wave N+1 consumes signatures wave N
changed, so the waves cannot overlap, and no two agents may hold the same file —
which is what the barrier enforces.

Each agent owns a vertical slice: its service, its unit specs under
`tests/services/`, and the integration specs that exercise it. Wave 3 agents work
in their own worktrees, since the nine files are interdependent.

Every brief carries the same non-negotiables:

- Verify with `pnpm test --filter=collaborative-state-worker`, then
  `pnpm test:integration` and `pnpm test:db` inside the package. Never bare
  `vitest`: turbo's `test: dependsOn: ["^build"]` is what keeps workspace deps
  built, and invoking vitest directly consumes whatever stale `dist/` is on disk.
- Convert whole transaction boundaries. A `db.transaction` must never call
  anything that writes through `query()` (D12).
- Do not touch tests outside the slice.
- Add no new `query()` call sites and no compensating shim. The raw path is being
  deleted, not preserved.
- Leave every tier green, or report precisely what is red and why.

### Parallel track — OpenTelemetry

Register a tracer provider and exporter that work in workerd, verify
`@kubiks/otel-drizzle` under `nodejs_compat`, decide the `db.statement`
question, then instrument (D11). Independent of the porting work in both
directions; the patcher is inert until the provider lands.

## Test fallout inventory

Permission to modify tests was given on 2026-08-20 and covers the whole
migration. This section is the inventory, not a request.

The dominant cost is not the 394 call sites but the **2646
`mockResolvedValueOnce` stubs** across 93 spec files. They are hand-written row
sets in the driver's snake_case, and the count is what the migration should be
budgeted by.

**652 of them (24%) return no rows.** They exist only to keep a positional mock
aligned: the code under test issues a query the test does not care about, so the
test must supply a placeholder to keep the following stub at the right index. A
keyed stub answers an unstubbed query with no rows by definition, so all 652
delete outright. `tests/services/checkpoint-service.spec.ts` has a single test
with 18 stubs of which 14 are padding.

**The remaining 1994 are the real work, and the point is to fix them, not to port
them.** A test that depends on the order its subject issues queries in breaks
whenever a query is added, removed or moved, which is exactly what this migration
does to every one of them. The stub therefore offers no sequencing facility, and
none should be added:

- Queries against different tables need no ordering at all. Keying by table and
  operation expresses them directly, and the test stops caring about call order.
- Assertions about what the code did belong on `calls(table).insert` and
  `statements`, which record every call with its parameters. Assert that a call
  with the right parameters happened, not that it happened third.
- A test that genuinely needs two different answers to the same query shape should
  discriminate on the parameters, not on a call index.
- A test issuing enough queries that none of the above helps is an integration
  test in a unit test's clothing. Split it, or move it to `tests/db`.

   until the parallel track lands. The guard's structured logs are the interim

   run in the default unit tier without Docker. Deferred: the stub keeps most

## Critical notes for implementing agents

- The database handle is ambient, always (D4). Ported code calls `db()` and
  `transaction()`; no function takes a handle and no route context carries one.
  Tests call the code under test directly; `stubDatabase()` and
  `createRealDatabaseConnection()` install the handle `db()` falls back to.
  Never mock `src/db`, and never wrap calls in `withDatabase` in a spec.
- Ported queries stay in the file that owned them. Do not create a
  `repositories/`, `queries/` or `dal/` module as part of a port; the
  abstraction is a separate decision (D3).
- A function that queries inside a transaction belongs in the same bucket as
  that transaction (D5). If a port reveals a call path the bucket pass missed,
  move the function, do not special-case it.
- Project-wide `eslint`/`tsc` in `workers/collaborative-state/` can hang on pre-existing issues;
  verify with targeted vitest runs and scoped lint during development.
- Postgres runs in Docker (`css-postgres`); use `docker exec` for psql access,
  never local `psql`.
- Applied drizzle-kit migrations are immutable; every schema change goes
  through editing `schema.ts` and generating a new migration, never through
  editing an existing file.
- Behavior parity is the acceptance bar for every PR (D9): if a ported query
  returns different rows, ordering, or errors than the original, the port is
  wrong even if tests pass.
